Where it cracks

Three cracks show up fast

01 · Ports
repo-a
:3000 repo-a
:3000
Two dev servers, one port. Address already in use — you juggle port numbers by hand.
02 · Hydration
wt/repo-a (fresh)
.env missing
node_modules/ missing
db seed missing
A raw worktree is empty. Copy env, install, seed — by hand, every single time.
03 · Multi-repo
one feature ↓
repo-a ⋮ repo-b
session = one repo
A feature spans two repos, but a session lives in one checkout — the second repo is out of reach.

And it gets worse over time: no lifecycle to archive or recover a feature, no shared memory between them, and a pile of tabs, folders, and branches you track in your head.

On disk

The whole runtime is one folder

~/mx/ the runtime — one folder ├── repos/ pristine clones (read-only) │ └── repo-a/git · repo-b/git · repo-c/git · repo-d/git ├── works/ one folder per feature │ ├── feature-a/ │ │ ├── wt/repo-a · wt/repo-b a worktree per repo │ │ ├── sessions/ session summaries │ │ └── work.json manifest (mx-owned) │ └── feature-b/ · feature-c/ · feature-d/ …more ├── context/ shared memory · institutional knowledge │ ├── INDEX.json the searchable index │ ├── auth/tokens.md how the system works │ ├── conventions/style.md team rules & conventions │ └── runbooks/deploy.md step-by-step runbooks ├── hooks/ lifecycle hooks │ ├── post-worktree-create hydrate: cp .env, install, seed │ └── session-prompt · work-health · repo-fetch … ├── bin/ dcs · lcs runtime-wide CLI helpers └── files/ creds.env · clusters.json shared operational values

mx owns the structure — work.json, the editor workspace, and ports are written only through mx commands. repos/ stay read-only; everything you build lives in works/<feature>/wt/.

Feature · worktrees

Many working copies, one clone

repos/repo-a/git
pristine clone · read-only
wt/repo-afeature-a
wt/repo-afeature-b
wt/repo-afeature-c

git worktrees let many branches be checked out at once, in separate folders, sharing one .git object store — full isolation with no duplicated repo on disk. mx creates and tracks them for you (mx work new / worktree add).

The one-session-one-repo wall, gone. A work groups a worktree per repo under one feature, so a single agent session edits across all of them — the change spanning repo-a + repo-b that a per-repo tab simply can't make together.

Feature · ports

Run the same app many times, side by side

localhost:3002up
repo-a · feature-a
localhost:3004up
repo-a · feature-b
localhost:3006up
repo-a · feature-c

The port clash, gone. mx allocates each feature its own ports, unique across the whole runtime — so the very same app (repo-a) runs three times at once, one per feature, each with its own live URL. mx work port set hands out a free one; the ports board shows who owns what.

Feature · hooks

A fresh worktree, ready to run

new worktree
mx work new / worktree add
cp .envconfig in place
pnpm installdeps ready
seed the dbdata ready
allocate portsno clashes

The hand-hydration, automated. The moment a worktree exists, mx fires the post-worktree-create hook — you decide what “ready” means (copy env, install, seed, …), in any language. It's one hub of lifecycle hooks: worktree create/remove, work archive/unarchive, repo fetch, health, and session-prompt.

Memory & lifecycle

Pause a feature, pick it up later

Active
Worktrees, ports, an agent session — and sessions/*.md notes as you go.
→mx work archive
Archived
Worktrees & ports freed. Branches and session summaries kept — recoverable.
→mx work unarchive
Back to work
Worktrees re-created; continue right where you left off.

The lifecycle you were missing. Every work keeps session summaries (sessions/*.md) — a distilled record of each session, so you or a fresh agent can resume cold. mx work archive frees the ports and worktrees but keeps the branches and notes; mx work unarchive brings it all back.
