# project-mx

Source and tooling for **mx** ("multiplexer") — a system for working on several features in parallel across multiple shared repos, using git worktrees. Each feature gets an isolated environment (its own worktrees, branches, ports, editor workspace, and terminal), so you can switch between features instantly without stashing or branch-juggling.

This repo is the **source of truth** for mx: it holds the CLI, the templates, and the docs. The thing it produces — a single `mx/` **runtime** with your cloned repos and live feature environments — lives in a separate folder on the device.

## Runtime vs. source

|             | what it is                          | where                     |
|-------------|--------------------------------------|---------------------------|
| **source**  | the mx tool, templates, and docs     | this repo (`project-mx/`) |
| **runtime** | clones + live feature environments   | one `mx/` folder per device |

The runtime's `CLAUDE.md` is **generated** from `templates/` here (run `mx update` to re-stamp it — never hand-edit the runtime copy). The per-work `work.json` and `.code-workspace` are **owned and generated by the `mx` CLI**, not by you: feature sessions read and mutate them only through `mx` commands. See `CLAUDE.md` for the source-of-truth and ownership rules.

## Finding the runtime

One device, one runtime. The CLI resolves its location in order:

1. `--runtime <path>` flag
2. `$MX_RUNTIME` environment variable
3. the path recorded in `.mx-runtime` (written by `mx init`, gitignored)

## Status

The `mx` CLI is a TypeScript pnpm monorepo: `@mx/core` (domain logic) + `apps/cli` (the CLI), bundled by tsup into `apps/cli/dist/bin/mx.js`. Commands: `init`, `status`, `update`, `repo`, and `work` (incl. `worktree`, `port`, `path`). `mx open` (terminal/editor layout) is deferred.

## Install (make `mx` global)

```bash
pnpm install
pnpm build           # bundles apps/cli/dist/bin/mx.js (re-run after code changes; `pnpm dev` watches)
```

`bin/mx` is a thin launcher kept on `$PATH` via `~/.zshrc`:

```bash
# ~/.zshrc
export PATH="$HOME/Projects/project-mx/bin:$PATH"
```

After that, `mx` works from any directory (re-open the shell or `source ~/.zshrc`); it runs the built `dist` output. You can also call `./bin/mx` directly. Editing a file under `templates/` takes effect immediately (no rebuild); changing CLI/core code needs `pnpm build` (or a running `pnpm dev`).

## Quick start

```bash
mx init ~/mx                      # scaffold/adopt a runtime, record its path
mx repo add <git-url>             # clone a pristine repo into the runtime
mx work new my-feature            # create a work
mx work -n my-feature worktree add <repo>   # add a worktree (ask the user first, in sessions)
mx work -n my-feature port set <repo> web   # allocate a free port
mx status                         # see everything
```

Feature sessions launched inside the runtime drive all of this through `mx` and never hand-edit `work.json`. The rules they follow live in `templates/CLAUDE.md`.

## CLI commands

| command | does |
|---|---|
| `mx init [path]` | scaffold/adopt a runtime (dirs, `.mx-root`, `CLAUDE.md`) and record its path |
| `mx status [--porcelain]` | list repos, works, worktrees, and ports |
| `mx update` | re-stamp the runtime's `CLAUDE.md` from the template |
| `mx repo add <git-url> [--name <n>]` | clone a pristine repo |
| `mx repo ls` / `mx repo -n <name> fetch\|info\|rm` | manage pristine repos |
| `mx work new <name> [--description <t>]` | create a work (manifest + workspace) |
| `mx work ls` / `mx work -n <name> info\|describe <t>` | manage works |
| `mx work -n <name> path` | print the work folder path (`cd "$(mx work -n <name> path)"`) |
| `mx work -n <name> worktree add\|ls\|rm <repo>` | manage a work's worktrees |
| `mx work -n <name> port set\|unset\|ls <repo> <service> [<port>]` | allocate/release ports |
| `mx work -n <name> destroy` | remove worktrees + work folder (keeps branches) |

Read commands take `--porcelain` for stable JSON; mutations echo the resulting object; errors are `{"error","code"}` with a non-zero exit.

`-n <name>` can be **omitted when your cwd implies it** — inside a work folder/worktree (`works/<work>/…`) mx infers the work (and the repo, in a worktree); inside `repos/<repo>/…` it infers the repo. An explicit `-n` always wins. `mx work new` prints the new work folder's absolute path.

## Development

```bash
pnpm typecheck     # tsc --noEmit across packages
pnpm lint          # eslint (typescript-eslint + jsdoc + prettier)
pnpm test          # vitest (unit tests for @mx/core)
pnpm build         # tsup bundle -> apps/cli/dist/bin/mx.js
pnpm dev           # tsup --watch (rebuild on change)
```

Domain logic lives in `packages/core` (`@mx/core`) as pure functions that return data and throw `MxError`; the CLI in `apps/cli` handles parsing, output, and exit codes. Add core logic with a Vitest test in `packages/core/test`. When testing against a sandbox runtime, set `MX_RUNTIME_POINTER` (and `MX_RUNTIME`) to a `/tmp` path so the real `.mx-runtime` is never touched.
